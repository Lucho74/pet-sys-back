Never add yourself as a co-author, contributor, or otherwise indicate that Claude/AI generated the work. This applies to:

## Project overview

"4 Patas" is a health/appointment management system for a 24-hour veterinary clinic. It replaces a paper-based record system and lets clients book appointments and view their pets' medical history. The clinic also handles hospitalizations (internación) and surgeries.

Three roles drive the functional scope (from the requirements gathering doc):

- **Client (Usuario)**: register, log in, edit own profile, book consultation appointments, view pet info and medical history, notify end of hospitalization.
- **Administrator**: create/edit/delete veterinarian profiles, manage veterinarians' schedules, suspend client accounts.
- **Veterinarian**: create a pet and assign it to a client, edit/delete pets, view client and pet info, schedule surgery/hospitalization appointments, manage a pet's medical history.

`Domain` (entities + validation + repository interfaces) and EF Core/SQL Server persistence in `Infrastructure` are wired up. `Application`/`Web` have CRUD for `User` (as `Client`), `Pet`, and `Consultation`. JWT login (`POST api/authentication/authenticate`) is implemented — see Cross-cutting decisions below — but role-based authorization on individual endpoints is not yet applied.

## Commands

This is a .NET 8 solution (`pet-sys-api.sln`) built with the standard `dotnet` CLI.

```
dotnet build                      # build the whole solution
dotnet build Domain                # build a single project (Domain, Application, Infrastructure, or Web)
dotnet run --project Web           # run the API (Swagger UI opens automatically in Development)
dotnet watch --project Web run     # run with hot reload
```

There is no test project yet. When one is added, run a single test with `dotnet test --filter FullyQualifiedName~TestName`.

`dotnet ef` is a **local tool** pinned in `dotnet-tools.json` (next to the `.sln`, `dotnet-ef` 8.0.10, matching EF Core) — run `dotnet tool restore` once, then `dotnet ef migrations add <Name> --project Infrastructure --startup-project Web` / `dotnet ef database update --project Infrastructure --startup-project Web`. The app does **not** migrate on startup: migrations are applied to Azure by the deploy workflow (see Persistence). Locally the whole team points user-secrets at the shared **dev** Azure SQL database, so running `dotnet ef database update` locally with a new, unmerged migration applies it to the shared dev database — avoid that; let the pipeline apply it after merge.

The Web project launches on `http://localhost:5079` (see `Web/Properties/launchSettings.json`), with Swagger UI at `/swagger` in the Development environment. `Web/Web.http` is a scratch file for manual REST Client requests against the running API.

## Architecture

Clean Architecture with four projects and a strict, one-directional dependency chain enforced by project references:

```
Domain  <-  Application  <-  Infrastructure  <-  Web
```

- **Domain**: POCO entities and enums only (`Domain/Entities/`). No dependencies on other projects. `Domain/Interfaces/` defines repository contracts: a generic `IBaseRepository<T>` (`GetByIdAsync`, `GetAllAsync`, `FindAsync`, `AddAsync`, `UpdateAsync`, `DeleteAsync`, `ExistsAsync`, all keyed by `int id`) plus entity-specific interfaces `IUserRepository`, `IPetRepository`, `IConsultationRepository` that extend it with query methods (e.g. `GetByClientIdAsync`, `GetByStatusAsync`, `GetByVeterinarianIdAsync`).
- **Application**: use cases/business logic. References `Domain`. `Models/` has `CreateUserDTO`/`UserDTO`, `CreatePetDTO`/`PetDTO`, `CreateConsultationDTO`/`ConsultationDTO`, and `WorkShiftDTO` (see Veterinarian work shifts below); `Services/UserServices.cs`, `Services/PetServices.cs`, and `Services/ConsultationServices.cs` implement CRUD for `User` (on `IUserRepository`), `Pet` (on `IPetRepository`), and `Consultation` (on `IConsultationRepository`) respectively, mapping manually to/from the DTOs — the object initializer is repeated inline at every return site rather than factored into a shared mapper method, even though it's repetitive; this is a deliberate user preference, not an oversight — and implement real interfaces (`IUserServices`, `IPetServices`, `IConsultationServices`) that DI resolves against (`AddScoped<IUserServices, UserServices>()`, same for `Pet`/`Consultation`). `Services/VeterinarianServices.cs` (`IVeterinarianServices`) is the one service that is **not** entity CRUD — it only reads/writes a `Veterinarian`'s work shifts, and injects `IUserRepository` rather than a repository of its own, since `Veterinarian` lives in the `User` TPH table. `Application/Exceptions/` has `NotFoundException` and `BadRequestException`: services throw these instead of returning `null`/`false` for "not found" or "invalid input" — see Cross-cutting decisions below for the full convention.
- **Infrastructure**: persistence and other external concerns. References `Domain` directly, **not** `Application` — the real reference chain today is `Domain <- Infrastructure <- Web`, skipping `Application` at the project-reference level (Web still references `Application` directly for DI). `Infrastructure/Context/ApplicationDbContext.cs` is a real EF Core `DbContext` on **`Microsoft.EntityFrameworkCore.SqlServer`**, pointed at **Azure SQL Database** (two separate databases, one per environment — see Persistence below). `Infrastructure/Repositories/BaseRepository<T>` is **EF-Core backed** (queries `_context.Set<T>()` directly) — it is not an in-memory `List<T>` implementation. `UserRepository`, `PetRepository`, `ConsultationRepository` extend `BaseRepository<T>` and implement their respective entity-specific interfaces (`ConsultationRepository` adds `GetByPetIdAsync`, `GetByVeterinarianIdAsync`, `GetByStatusAsync`). There is no `IDesignTimeDbContextFactory` — `dotnet ef` resolves `ApplicationDbContext` from `Web`'s host (the `AddDbContext` registration in `Program.cs`, run in the `Development` environment so user-secrets apply), so always pass both projects: `dotnet ef migrations add <Name> --project Infrastructure --startup-project Web` (same flags for `database update`). Migrations live in `Infrastructure/Migrations`.
- **Web**: ASP.NET Core Web API host (`Web/Program.cs`), references both `Application` and `Infrastructure`. Registers `ApplicationDbContext` via `AddDbContext`/`UseSqlServer` with no connection-retry strategy — `EnableRetryOnFailure()` was considered and deliberately left out to match the class reference repo, which doesn't use it. Known trade-off: the Azure SQL databases are free-tier serverless and auto-pause when idle, so the first request after a pause can fail with a transient connection error while the database resumes (the workflow's "Wake up database" step only covers deploy time). It does **not** call `Database.Migrate()` on startup — schema changes are applied by the deploy workflow. Also wires DI for `IUserRepository`/`IUserServices`, `IPetRepository`/`IPetServices`, `IConsultationRepository`/`IConsultationServices`, plus `AddAuthentication(JwtBearerDefaults.AuthenticationScheme).AddJwtBearer(...)` reading `Authentication:Issuer`/`Audience`/`SecretForKey` from configuration, and a global exception handler (`AddExceptionHandler<AppExceptionHandler>()` + `AddProblemDetails()` + `app.UseExceptionHandler()`) — `Web/ExceptionHandling/AppExceptionHandler.cs` implements .NET 8's `IExceptionHandler`, mapping `NotFoundException`→`404`, `BadRequestException`→`400`, and `UnauthorizedException`→`401`; anything else falls through (`TryHandleAsync` returns `false`) to the default 500 behavior. The middleware pipeline calls `app.UseAuthentication()` before `app.UseAuthorization()`. `Controllers/UserController.cs`, `Controllers/PetController.cs`, and `Controllers/ConsultationController.cs` each expose full REST CRUD (`GET`/`GET {id}`/`POST`/`PUT {id}`/`DELETE {id}`) at `api/user`, `api/pet`, and `api/consultation` respectively, and neither does any null-checking itself — they just call the service and let exceptions propagate to the handler. `ConsultationController` additionally exposes `GET api/consultation/pet/{petId}`, `GET api/consultation/veterinarian/{veterinarianId}`, and `GET api/consultation/status/{status}` as filter endpoints, and `PetController` exposes `GET api/pet/client/{clientId}`; all of these, along with every CRUD action on all three controllers, now carry `[Authorize(Roles = "...")]` attributes (see Auth note below for the exact role matrix). `Controllers/AuthenticationController.cs` exposes `POST api/authentication/authenticate` (takes a `LoginDTO`, calls `IUserServices.AuthenticateAsync`, returns `{ token }` with `sub`/role claims — no email claim) and is the only endpoint left unauthenticated, as it must be to issue the token in the first place. `Controllers/VeterinarianController.cs` exposes `GET`/`PUT api/veterinarian/me/work-shifts` with a controller-level `[Authorize(Roles = "Veterinarian")]` — see Veterinarian work shifts below for why these are a separate controller instead of two more actions on `UserController`. Action method names match the verb used at the repository/service layer for that HTTP verb (`Add{Entity}` for `POST`, not `Create{Entity}`) — keep this alignment (`AddAsync`/`Add{Entity}Async`/`Add{Entity}`, `UpdateAsync`/.../`Update{Entity}`, etc.) across all three layers when adding new entities.

### Domain model

- `User` (`Domain/Entities/User.cs`) is an **abstract base class** with `Id`, `FullName`, `Password`, `Email`, `Phone`, and a soft-delete flag `IsDeleted`. Validation is expressed via `System.ComponentModel.DataAnnotations` attributes (`[Required]`, `[StringLength]`, `[EmailAddress]`, `[Phone]`) rather than in constructors/methods.
- Three concrete roles inherit from `User`, matching the three roles above: `Client` (adds `Dni` and a `Pets` collection), `Admin` (no extra fields), `Veterinarian` (adds a `Consultations` collection and `WorkShifts`, a `List<WorkShift>` persisted as JSON — see Veterinarian work shifts below). This maps directly to the client/administrator/veterinarian roles in the requirements — role-specific behavior belongs on these subclasses or in services that branch on role, not on `User` itself.
  - A fourth concrete role, `SysAdmin` (`Domain/Entities/SysAdmin.cs`, no extra fields beyond `User`), was added later and is registered as an additional TPH discriminator value (`HasValue<SysAdmin>("SysAdmin")`, see below) and granted the broadest controller access (`[Authorize(Roles = "SysAdmin,Admin")]`/`"SysAdmin,Admin,Veterinarian"`, etc. — always listed first). It is **not** in `Domain/Entities/UserType.cs`'s enum, so `CreateUserDTO.UserType`'s `switch` in `UserServices.AddUserAsync` has no case for it — there is currently no API path that creates a `SysAdmin`; one must be inserted directly in the database (e.g. via the dev seed script or a manual insert) if needed. Treat this as the current state, not a bug to silently fix.
  - `Domain/Entities/UserType.cs` is a plain enum (`Admin`, `Client`, `Veterinarian`) used only at the DTO layer to pick which concrete subclass to instantiate — it is **not** the EF discriminator column (that's the separate `"UserType"` string discriminator from `HasDiscriminator<string>`, below). `CreateUserDTO.UserType` (`[JsonConverter(typeof(JsonStringEnumConverter))]`, defaults to `UserType.Client`) drives a `switch` in `UserServices.AddUserAsync` that constructs a `Client`/`Admin`/`Veterinarian` accordingly. `Dni` is carried on both `CreateUserDTO` and `UserDTO` (`[StringLength(20)]`, nullable) but only ever populated for `Client`s — `AddUserAsync` sets it from `dto.Dni` in the `Client` branch and leaves it out of the `Admin`/`Veterinarian` branches; `GetAllUserAsync`'s mapping mirrors this with `user is Client client ? client.Dni : null`. `UserDTO.RoleName` (`user.GetType().Name`) is how a caller tells which concrete role a `GET` result is.
- `Pet` belongs to a `Client` (`ClientId` FK) and has many `Consultation`s. All entity IDs and FK properties (`Pet.Id`/`ClientId`, `Consultation.Id`/`PetId`/`VeterinarianId`) are typed as `int`, matching `User.Id` — keep this convention when adding related entities.
- `Domain/Interfaces/IBaseRepository<T>` and its EF-Core-backed `Infrastructure/Repositories/BaseRepository<T>` key all lookups by `int id`, consistent with the `int` entity ID convention.
  - `BaseRepository<T>.GetByIdAsync` returns `null` (via `FirstOrDefaultAsync`) when the id doesn't exist — it does **not** throw; repository-level "not found" is still a plain `null`, only the `Application` layer above it turns that into `NotFoundException` (see Cross-cutting decisions). `DeleteAsync` is a no-op on a missing id; `ExistsAsync` returns `false`. `UpdateAsync` looks the entity up first and returns `null` if missing, otherwise applies `CurrentValues.SetValues` and saves.
  - `T` must implement `Domain.Interfaces.IEntity` (constrained via `where T : class, IEntity`) rather than relying on reflection over an `Id` property.
- `Consultation` links a `Pet` and a `Veterinarian`, with a `Status` (`StatusConsultation` enum: `Pending`, `Completed`, `Cancelled` — tagged `[JsonConverter(typeof(JsonStringEnumConverter))]` so it serializes as the string name, not the underlying `int`) and a `Date`. `Date` is the **start instant** of the appointment and is mapped as `datetime2`; it was previously mapped `HasColumnType("date")` (date only, no time of day) with a matching `[DataType(DataType.Date)]` annotation on the entity, and both were removed when appointment scheduling landed, because a turno needs an hour. This is the appointment/consultation entity referenced by the "agendar turnos" and "historial médico" features. `ConsultationServices.AddConsultationAsync` always sets `Status = StatusConsultation.Pending` on create (a new consultation starts pending, like booking an appointment) — `CreateConsultationDTO` deliberately has no `Status` field for this reason; `ConsultationDTO` (used for `GET`/`PUT`) does include `Status` so a vet/admin can move it to `Completed`/`Cancelled` via `PUT`. Both `AddConsultationAsync` and `UpdateConsultationAsync` validate `PetId` (must resolve via `IPetRepository.GetByIdAsync`) and `VeterinarianId` (must resolve via `IUserRepository.GetByIdAsync` to a `Veterinarian`, not just any `User`) before saving, throwing `BadRequestException` otherwise — same cross-entity-validation convention as `PetServices.AddPetAsync`'s `ClientId` check. Both then call the private `ConsultationServices.ValidateSlotAsync`, which enforces the appointment-slot rules described under Veterinarian work shifts below.
  - **Open question**: how hospitalizations/surgeries should be modeled is not yet decided. Options considered: extend `Consultation` with a `Type` field (Consulta/Cirugía/Internación), or add separate `Surgery`/`Hospitalization` entities linked to `Pet`. Resolve this before implementing the veterinarian's "agendar turnos de cirugías e internaciones" feature.
- "Notificar fin de internación" (listed under the client's functionalities in the requirements doc) is actually the **system notifying the client** that their pet's hospitalization has ended — not a client-initiated action. Model it as a notification triggered by a status change (e.g., a vet/admin marking hospitalization complete), not as an endpoint the client calls.
- `ApplicationDbContext` maps the `User` hierarchy (`Client`/`Admin`/`Veterinarian`/`SysAdmin`) via `HasDiscriminator<string>("UserType")`, i.e. **TPH (Table-Per-Hierarchy)** — note this contradicts the TPT decision this file documented earlier; if TPT is still the intended design, `OnModelCreating` needs `UseTptMappingStrategy()` instead of the discriminator, otherwise treat TPH as the now-current decision. `Pet`/`Consultation` FKs cascade-delete from their parent (`Client`→`Pet`, `Pet`→`Consultation`), while `Consultation`→`Veterinarian` is `Restrict`.

### Veterinarian work shifts and appointment slots

A veterinarian's weekly availability is `Veterinarian.WorkShifts`, a `List<WorkShift>?` persisted as **JSON in a single `nvarchar(1000)` column** on the `Users` table via an EF **value converter** (`HasConversion` with `JsonSerializer`, configured in `ApplicationDbContext`). `WorkShift` (`Domain/Entities/WorkShift.cs`) is a `record` value object — `Day`/`StartTime`/`EndTime`, no `Id`, no table, not an `IEntity` — and is a record on purpose, because the value comparer below relies on its value equality.

The property is **nullable** to match the TPH table, where `Client`/`Admin`/`SysAdmin` rows have no value in that column, and so that the column shape stays exactly what the original migration created. Changing it to a non-nullable `List<WorkShift>` would need a migration plus a backfill, and would still read back as `null` for non-veterinarian rows.

Three mapping choices were considered; this is why the converter won:

- **A child table or an `OwnsMany(...)` collection** was rejected mainly because `BaseRepository<T>.UpdateAsync` persists with `CurrentValues.SetValues`, which copies **scalar properties only** — navigations and owned collections are not copied. It happens not to bite in the current call sites, since every service loads a tracked entity and mutates it so EF's change tracker does the work regardless; the problem is latent. The moment someone uses `UpdateAsync(id, entity)` the way its signature invites — handing it a detached entity built from a DTO — scalar edits would save and collection edits would vanish with no error. A converted property is a scalar in the EF model, so both behave the same.
- **`OwnsMany(...).ToJson()`** was additionally avoided because `Veterinarian` sits in the `Users` TPH hierarchy, and owned JSON on a derived type in TPH has known rough edges in EF Core 8. This was never actually tested — the converter simply has no such uncertainty.
- **An opaque `string` on the entity** (the first implementation) worked but leaked the serialization format into every consumer and gave up type safety at the entity boundary.

The converter is registered with an explicit **`ValueComparer`**, and it is not optional: for a mutable reference type like `List<T>`, EF's default comparison is by reference, so replacing the list is detected but editing it in place is silently never saved. The services happen to always assign a fresh list, but the comparer is what makes that safe to stop doing.

`WorkShift` carries `[JsonConverter(typeof(JsonStringEnumConverter))]` on `Day` so the stored JSON reads `"Saturday"` rather than `6`. `Application` keeps its own `WorkShiftDTO` as the API contract and `VeterinarianServices` maps between the two by hand, per the manual-mapping convention; no service serializes JSON itself any more.

Rules enforced today:

- **Fixed 30-minute slots.** `ConsultationServices.SlotMinutes` is a `const int`, not a column: `Consultation` has no duration field and `CreateConsultationDTO` takes no duration. Variable-length appointments — which the surgery/hospitalization open question above will probably need — would mean adding that column.
- **A turno must fit entirely inside one shift** for that `DayOfWeek`, compared against the appointment's own date (`start.Date + shift.StartTime`), so a slot that would spill past midnight is rejected instead of wrapping around.
- **Overnight shifts must be split into two entries** (e.g. Saturday 22:00–23:59 plus Sunday 00:00–06:00). `UpdateWorkShiftsAsync` rejects `EndTime <= StartTime` with a `BadRequestException` precisely so a wrap-around shift can never be stored, which is what keeps the comparison above correct — don't "fix" this by permitting it without reworking the slot check too.
- **No double-booking**: a vet cannot hold two non-`Cancelled` consultations whose 30-minute slots overlap. Implemented with `IBaseRepository.FindAsync` over a ±30-minute window around the start (strict inequalities, so back-to-back turnos are allowed), excluding the consultation being edited on `PUT`. It is a check-then-insert, so two concurrent requests can both pass it; closing that properly needs a unique index or a transaction.
- **A veterinarian with no shifts stored is unrestricted** — the shift check is skipped entirely and only the overlap rule applies. This is deliberate: it keeps seeded consultations and any veterinarian created before this feature working, instead of making every `POST api/consultation` fail until somebody fills in a schedule.

Only the veterinarian sets their own shifts, via `PUT api/veterinarian/me/work-shifts` reading the `sub` claim. The requirements doc files "manage veterinarians' schedules" under the **Administrator**, so an admin-facing `api/veterinarian/{id}/work-shifts` is still missing.

`VeterinarianController` is a separate controller rather than two more actions on `UserController` because of an ASP.NET Core detail worth remembering: **controller-level and action-level `[Authorize]` attributes are combined (AND), not overridden**. `UserController`'s class-level `[Authorize(Roles = "SysAdmin,Admin")]` therefore applies to every action in it, so a `Veterinarian`-only action added there would be unreachable for veterinarians.

## Cross-cutting decisions

- **Auth**: JWT-based authentication (`Microsoft.AspNetCore.Authentication.JwtBearer`), with **BCrypt** (`BCrypt.Net-Next` package in `Application`, not ASP.NET Core Identity) used for password hashing — `BCrypt.Net.BCrypt.HashPassword(...)`/`BCrypt.Net.BCrypt.Verify(...)`, called directly from `UserServices` (no DI'd hasher abstraction). `UserServices.AddUserAsync`/`UpdateUserAsync` hash `Password` before persisting; `UserServices.AuthenticateAsync(LoginDTO)` looks the user up via `IUserRepository.GetByEmailAsync` and verifies with `BCrypt.Net.BCrypt.Verify`, throwing `Application.Exceptions.UnauthorizedException` (→ `401`, see error-handling convention below) on a bad/missing credential or a soft-deleted user, otherwise returning a `UserDTO` — deliberately populated with only `Id`/`RoleName` (the rest of `UserDTO`'s properties are left at their default, since this DTO instance is only ever read internally by the controller for claim-building, never serialized back to a client; don't reuse this particular `AuthenticateAsync` return value anywhere that expects a fully-populated `UserDTO`). `AuthenticationController.Authenticate` turns that into a JWT (a `sub` claim with `UserDTO.Id` and a `ClaimTypes.Role` claim with `UserDTO.RoleName` — deliberately no email claim) signed with `Authentication:SecretForKey` (HMAC-SHA256), flat 1-hour expiry for every role. **Future/not implemented**: per-role expiration (e.g. a shorter-lived token for `Admin`) — flagged with a `TODO` at the `DateTime.UtcNow.AddHours(1)` call in `AuthenticationController`, no design decided yet (simplest option would be a `switch` on `user.RoleName` returning a `TimeSpan`, added to `DateTime.UtcNow`). `Authentication:Issuer`/`Audience` live in `Web/appsettings.json`; `Authentication:SecretForKey` is deliberately **not** committed — it must be at least 32 characters (HMAC-SHA256), and the team uses the **same value locally and in the deployed dev App Service** (a deliberate choice). It lives only in each developer's `dotnet user-secrets` (`Web` project has a `UserSecretsId`) and in the App Service app setting `Authentication__SecretForKey`. Because it's the real deployed key, it must never go into a committed file — that's why there is no `appsettings.Development.json` holding it. GitHub Actions secrets are **not** used for app configuration: the app reads its config at runtime from App Service environment variables, which are set manually in the portal. Existing DB rows created before this hashing change still have plaintext passwords and won't authenticate until re-saved through `AddUserAsync`/`UpdateUserAsync`. **Role-based authorization is now implemented** (added after the rest of this section was first written — JWT issuance/validation came first, enforcement followed later): every controller action carries an `[Authorize(Roles = "...")]` attribute, either at the controller level (`UserController`, restricted to `"SysAdmin,Admin"` for all of `GET`/`GET {id}`/`POST`/`PUT`/`DELETE`) or per-action (`PetController`, `ConsultationController`). The pattern is: full CRUD on `Pet`/`Consultation` is `"SysAdmin,Admin,Veterinarian"`; the `Client`-facing filter endpoints are opened up further by adding `Client` to that list — `PetController`'s `GET api/pet/client/{clientId}` and `ConsultationController`'s `GET api/consultation/pet/{petId}` are `"SysAdmin,Admin,Veterinarian,Client"`, while `ConsultationController`'s `GET api/consultation/veterinarian/{veterinarianId}` and `GET api/consultation/status/{status}` stay at `"SysAdmin,Admin,Veterinarian"` (no `Client` case to open them to). `AuthenticationController.Authenticate` remains the only unauthenticated endpoint, as it must be. `UserController` also exposes `GET api/user/me` (`[Authorize]` with no role restriction, placed above the controller-level `[Authorize(Roles = "SysAdmin,Admin")]`) so any authenticated user can fetch their own `UserDTO` by reading the `sub` claim (`ClaimTypes.NameIdentifier` once ASP.NET Core's default inbound claim mapping runs) off `User.FindFirstValue` and calling `GetUserByIdAsync` — this exists precisely because the rest of `UserController` is `Admin`/`SysAdmin`-only, so a `Client`/`Veterinarian` would otherwise have no way to read their own profile. The route doesn't collide with `GET api/user/{id:int}` since `{id:int}`'s route constraint never matches the literal `me`. **Known bug**: `/me` does not actually achieve that — controller-level and action-level `[Authorize]` attributes are combined (AND), not overridden, so the class-level `Roles = "SysAdmin,Admin"` still applies and a `Client`/`Veterinarian` gets `403`. Fixing it means moving the action onto its own controller or splitting `UserController`; `VeterinarianController` was created as a separate controller for exactly this reason. The `[Authorize(Roles = ...)]` checks are enforced purely on the `ClaimTypes.Role` claim set at login time (see above) — there is no resource-level check (e.g. a `Client` calling `GET api/pet/client/{clientId}` with somebody else's `clientId` is not blocked by role alone; whether that needs an additional ownership check is also undecided).
- **DTO mapping**: manual mapping (constructors/explicit mapper methods) between `Domain` entities and Application/Web DTOs — no AutoMapper or similar. See `UserServices` for the established pattern.
- **Input validation**: DataAnnotations on the DTOs (mirroring the constraints on the corresponding `Domain` entity) plus `[ApiController]`'s automatic `ModelState` validation — invalid input short-circuits with `400` before the controller action runs.
- **Error handling / "not found"**: services throw `Application.Exceptions.NotFoundException`, `BadRequestException`, or `UnauthorizedException` (the latter added for `UserServices.AuthenticateAsync` → `401`) instead of returning `null`/`false` or using a tuple return — this **replaces** the earlier null-return/tuple convention (an older iteration of this codebase used bare `null`/`false` plus manual `if (x == null) return NotFound();` checks in every controller action, and `PetServices.UpdatePetAsync` briefly returned a `(PetDTO?, bool)` tuple to distinguish "not found" from "invalid ClientId" before exceptions existed; both are gone now). `Web/ExceptionHandling/AppExceptionHandler.cs` (a .NET 8 `IExceptionHandler`) is the single place that maps exception type → HTTP status code; controllers should never `try/catch` or null-check service results themselves — just call the service and return `Ok`/`CreatedAtAction`/`NoContent` directly, same as `UserController`/`PetController`. Cross-entity validation (e.g. `Pet.ClientId` must reference an existing `Client`) now throws `BadRequestException` from `PetServices.AddPetAsync`/`UpdatePetAsync` (both inject `IUserRepository` and check `is not Client`) instead of returning `null`/a tuple. Any exception type not handled by `AppExceptionHandler` falls through to the default 500 behavior, so add a case there (not a controller-level catch) when a new failure mode needs its own status code.
- **Persistence**: SQL Server via EF Core/`Microsoft.EntityFrameworkCore.SqlServer`, hosted on **Azure SQL Database** (decided — see Architecture/Infrastructure above). This replaces the earlier Postgres/Supabase setup; a local-SQLite alternative was evaluated and explicitly rejected in favor of this. Two separate Azure SQL databases, one per environment, each in its own Azure resource group (dev and prod resource groups already exist; a teammate provisions the actual SQL servers/databases — not something driven from this repo). `Web/appsettings.json`'s `ConnectionStrings:DefaultConnection` is deliberately left empty — the real value is supplied per-environment, never committed: locally via `dotnet user-secrets set "ConnectionStrings:DefaultConnection" "..."` (mirrors the existing `Authentication:SecretForKey` pattern, same `UserSecretsId`), and in the deployed Azure App Service via an app setting named `ConnectionStrings__DefaultConnection` (set manually in the Azure portal/CLI). The GitHub Actions workflow at `.github/workflows/main_pet-sys-app.yml` (one level up from this solution) follows the class reference repo (`github.com/PabloPaezSheridan/pl2026_classapi`): push to `main` deploys the `dev` GitHub Environment; `workflow_dispatch` lets you pick `dev`/`prod`. The deploy job logs into Azure, restores the `dotnet-ef` local tool, adds the runner's public IP to the SQL server firewall (`github-runner-${{ github.run_id }}`), wakes the auto-paused database (`SELECT 1`, 3 attempts), runs `dotnet ef database update` with `ConnectionStrings__DefaultConnection` from the secret, removes the firewall rule (`if: always()`), then deploys to the App Service named by `vars.AZURE_WEBAPP_NAME` (a deviation from the reference, which hardcodes the dev app name). Per-environment GitHub config it expects — **secrets**: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_SQL_CONNECTION_STRING`; **variables**: `AZURE_SQL_RESOURCE_GROUP`, `AZURE_SQL_SERVER_NAME`, `AZURE_WEBAPP_NAME`. The `azure/login` identity needs rights on the SQL server (firewall rules) as well as the App Service. The App Service itself still needs its runtime app settings (`ConnectionStrings__DefaultConnection`, `Authentication__SecretForKey`) set in the portal — the workflow doesn't push them. `main` is the **dev** branch (App Service `pet-sys-app`); prod has its own Azure SQL server/database/App Service and is deployed via the `prod` environment. Azure SQL access: the server firewall has "Allow Azure services" enabled (so the App Service connects), and each developer's public IP must be added to the server's firewall (Networking) to connect from their machine — home/university IPs change, so re-add when a connection is refused.
  - **Dev seed data**: `Scripts/seed-dev.sql` is a plain T-SQL script (not a project, not part of the build) that fills the **dev** Azure SQL database with test data — 105 users (5 `Admin`, 15 `Veterinarian`, 85 `Client`), 20 pets, 40 consultations — run manually from SSMS/Azure Data Studio/the Azure portal query editor/`sqlcmd` after the schema exists (i.e. after the first deploy has run the migrations). It inserts explicit IDs (`SET IDENTITY_INSERT`), writes the TPH discriminator `UserType` directly, does nothing if `Users` already has rows, and dates consultations relative to `GETDATE()` (future ones `Pending`). Every seeded user's password is `Password123!` (a single precomputed BCrypt hash). Because it's raw SQL against the table schema, it must be updated by hand whenever a migration changes `Users`/`Pets`/`Consultations`. It does not populate `Users.WorkShifts`, so every seeded veterinarian is unrestricted as far as appointment slots go (see Veterinarian work shifts above). The prod database intentionally starts empty (schema only, via the workflow's migration step).
  - **Known issue (historical)**: the old Supabase connection string (with password) was committed in plaintext in `Web/appsettings.json` before this migration. The string has been removed from the file, but it's still present in git history — the Supabase credential should still be rotated independently of this change.
- **Testing**: no test project exists yet on `main`; framework not decided.
- **Frontend**: a separate SPA (React/Angular/etc., own repo) will consume this API. `Web/Program.cs` registers a permissive CORS policy (`"AllowAll"`: `AllowAnyOrigin`/`AllowAnyMethod`/`AllowAnyHeader`) applied globally via `app.UseCors("AllowAll")` before `UseAuthorization()` — fine for now with no auth, but tighten this (specific origins, not any) once JWT auth lands so credentials/tokens aren't exposed to arbitrary origins.
