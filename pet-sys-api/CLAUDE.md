## Project overview

"4 Patas" is a health/appointment management system for a 24-hour veterinary clinic. It replaces a paper-based record system and lets clients book appointments and view their pets' medical history. The clinic also handles hospitalizations (internación) and surgeries.

Three roles drive the functional scope (from the requirements gathering doc):

- **Client (Usuario)**: register, log in, edit own profile, book consultation appointments, view pet info and medical history, notify end of hospitalization.
- **Administrator**: create/edit/delete veterinarian profiles, manage veterinarians' schedules, suspend client accounts.
- **Veterinarian**: create a pet and assign it to a client, edit/delete pets, view client and pet info, schedule surgery/hospitalization appointments, manage a pet's medical history.

`Domain` (entities + validation + repository interfaces) and EF Core/SQL Server persistence in `Infrastructure` are wired up. `Application`/`Web` have CRUD for `User` (as `Client`), `Pet`, and `Consultation`. JWT login (`POST api/authentication/authenticate`) is implemented and every endpoint carries role-based authorization — see Cross-cutting decisions below.

## Commands

This is a .NET 8 solution (`pet-sys-api.sln`) built with the standard `dotnet` CLI.

```
dotnet build                      # build the whole solution
dotnet build Domain                # build a single project (Domain, Application, Infrastructure, or Web)
dotnet run --project Web           # run the API (Swagger UI opens automatically in Development)
dotnet watch --project Web run     # run with hot reload
```

There is no test project yet. When one is added, run a single test with `dotnet test --filter FullyQualifiedName~TestName`.

`dotnet ef` is a **local tool** pinned in `dotnet-tools.json` (next to the `.sln`, `dotnet-ef` 8.0.10, matching EF Core) — run `dotnet tool restore` once, then `dotnet ef migrations add <Name> --project Infrastructure --startup-project Web` / `dotnet ef database update --project Infrastructure --startup-project Web`. The app does **not** migrate on startup: migrations are applied to Azure by the deploy workflow (see Persistence). Locally the whole team points user-secrets at the shared **dev** Azure SQL database, so running `dotnet ef database update` locally with a new, unmerged migration applies it to the shared dev database — avoid that; let the pipeline apply it after merge.

The Web project launches on `http://localhost:5079` (see `Web/Properties/launchSettings.json`), with Swagger UI at `/swagger` in the Development environment. `Web/Web.http` is a scratch file for manual REST Client requests against the running API.

## Architecture

Clean Architecture with four projects and a strict, one-directional dependency chain enforced by project references:

```
Domain  <-  Application  <-  Infrastructure  <-  Web
```

- **Domain**: POCO entities and enums only (`Domain/Entities/`). No dependencies on other projects. `Domain/Interfaces/` defines repository contracts: a generic `IBaseRepository<T>` (`GetByIdAsync`, `GetAllAsync`, `FindAsync`, `AddAsync`, `UpdateAsync`, keyed by `int id`; there is no `DeleteAsync`, since nothing is physically deleted through the API) plus entity-specific interfaces `IUserRepository`, `IPetRepository`, `IConsultationRepository` that extend it with query methods (e.g. `GetByClientIdAsync`, `GetByPetIdAsync`, `GetByVeterinarianIdAsync`).
- **Application**: use cases/business logic. References `Domain`. `Models/` splits input from output DTOs: `CreateUserDTO`/`UpdateUserDTO` in, `UserDTO` out (no `Password`); `CreateEditPetDTO` in (both `POST` and `PUT`), `PetDTO` out; `CreateEditConsultationDTO` in (both `POST` and `PUT`), `ConsultationDTO` out. Output DTOs carry `Id` and `IsDeleted`, input DTOs do not, so a client can never set them; `Services/UserServices.cs`, `Services/PetServices.cs`, and `Services/ConsultationServices.cs` implement CRUD for `User` (on `IUserRepository`), `Pet` (on `IPetRepository`), and `Consultation` (on `IConsultationRepository`) respectively, mapping manually to/from the DTOs — the object initializer is repeated inline at every return site rather than factored into a shared mapper method, even though it's repetitive; this is a deliberate user preference, not an oversight — and implement real interfaces (`IUserServices`, `IPetServices`, `IConsultationServices`) that DI resolves against (`AddScoped<IUserServices, UserServices>()`, same for `Pet`/`Consultation`). `Application/Exceptions/` has `NotFoundException`, `BadRequestException`, `UnauthorizedException` and `ForbiddenException`: services throw these instead of returning `null`/`false` for "not found" or "invalid input" — see Cross-cutting decisions below for the full convention.
- **Infrastructure**: persistence and other external concerns. References `Domain` directly, **not** `Application` — the real reference chain today is `Domain <- Infrastructure <- Web`, skipping `Application` at the project-reference level (Web still references `Application` directly for DI). `Infrastructure/Context/ApplicationDbContext.cs` is a real EF Core `DbContext` on **`Microsoft.EntityFrameworkCore.SqlServer`**, pointed at **Azure SQL Database** (two separate databases, one per environment — see Persistence below). `Infrastructure/Repositories/BaseRepository<T>` is **EF-Core backed** (queries `_context.Set<T>()` directly) — it is not an in-memory `List<T>` implementation. `UserRepository`, `PetRepository`, `ConsultationRepository` extend `BaseRepository<T>` and implement their respective entity-specific interfaces (`ConsultationRepository` adds `GetByPetIdAsync`, `GetByVeterinarianIdAsync`). There is no `IDesignTimeDbContextFactory` — `dotnet ef` resolves `ApplicationDbContext` from `Web`'s host (the `AddDbContext` registration in `Program.cs`, run in the `Development` environment so user-secrets apply), so always pass both projects: `dotnet ef migrations add <Name> --project Infrastructure --startup-project Web` (same flags for `database update`). Migrations live in `Infrastructure/Migrations`.
- **Web**: ASP.NET Core Web API host (`Web/Program.cs`), references both `Application` and `Infrastructure`. Registers `ApplicationDbContext` via `AddDbContext`/`UseSqlServer` with EF Core's SQL Server retrying execution strategy (`EnableRetryOnFailure(maxRetryCount: 5, maxRetryDelay: 30s)`). This was originally left out to match the class reference repo and later added on purpose: the Azure SQL databases are free-tier serverless and auto-pause when idle, so the first request after a pause used to fail with a transient error (e.g. 40613, database not currently available) while the database resumed — the workflow's "Wake up database" step only covers deploy time. With the retry strategy that request is retried with exponential backoff instead of failing, at the cost of a slow first response (can take tens of seconds). Resume can take up to ~1 minute, so the connection string should also carry a higher `Connect Timeout` (e.g. 60) — that lives in user-secrets/App Service settings, not in the repo. Any future explicit transaction (`BeginTransaction`) must be wrapped in `context.Database.CreateExecutionStrategy().ExecuteAsync(...)`, otherwise EF throws with a retrying strategy enabled; none exist today. A circuit breaker (Polly) was discussed and deferred. It does **not** call `Database.Migrate()` on startup — schema changes are applied by the deploy workflow. Also wires DI for `IUserRepository`/`IUserServices`, `IPetRepository`/`IPetServices`, `IConsultationRepository`/`IConsultationServices`, plus `AddAuthentication(JwtBearerDefaults.AuthenticationScheme).AddJwtBearer(...)` reading `Authentication:Issuer`/`Audience`/`SecretForKey` from configuration, and a global exception handler (`AddExceptionHandler<AppExceptionHandler>()` + `AddProblemDetails()` + `app.UseExceptionHandler()`) — `Web/ExceptionHandling/AppExceptionHandler.cs` implements .NET 8's `IExceptionHandler`, mapping `NotFoundException`→`404`, `BadRequestException`→`400`, `UnauthorizedException`→`401`, and `ForbiddenException`→`403`; anything else falls through (`TryHandleAsync` returns `false`) to the default 500 behavior. The middleware pipeline calls `app.UseAuthentication()` before `app.UseAuthorization()`. `Controllers/UserController.cs`, `Controllers/PetController.cs`, and `Controllers/ConsultationController.cs` expose `GET`/`GET {id}`/`POST`/`PUT {id}` at `api/user`, `api/pet`, and `api/consultation` respectively (`UserController` also has `DELETE {id}`, which suspends; `Pet`/`Consultation` have no `DELETE` endpoint), and neither does any null-checking itself — they just call the service and let exceptions propagate to the handler. `ConsultationController` additionally exposes `GET api/consultation/pet/{petId}`, and `GET api/consultation/veterinarian/{veterinarianId}` as filter endpoints, and `PetController` exposes `GET api/pet/client/{clientId}` and `GET api/pet/me`; all of these, along with every CRUD action on all three controllers, now carry `[Authorize(Roles = "...")]` attributes (see Auth note below for the exact role matrix). `Controllers/AuthenticationController.cs` exposes `POST api/authentication/authenticate` (takes a `LoginDTO`, calls `IUserServices.AuthenticateAsync`, returns the JWT as a plain string body, not a `{ token }` object, with `sub`/role claims — no email claim) and is the only endpoint left unauthenticated, as it must be to issue the token in the first place. Action method names match the verb used at the repository/service layer for that HTTP verb (`Add{Entity}` for `POST`, not `Create{Entity}`) — keep this alignment (`AddAsync`/`Add{Entity}Async`/`Add{Entity}`, `UpdateAsync`/.../`Update{Entity}`, etc.) across all three layers when adding new entities.

### Domain model

- `User` (`Domain/Entities/User.cs`) is an **abstract base class** with `Id`, `FullName`, `Password`, `Email`, `Phone`, and a soft-delete flag `IsDeleted`. Validation is expressed via `System.ComponentModel.DataAnnotations` attributes (`[Required]`, `[StringLength]`, `[EmailAddress]`, `[Phone]`) rather than in constructors/methods.
- Three concrete roles inherit from `User`, matching the three roles above: `Client` (adds `Dni` and a `Pets` collection), `Admin` (no extra fields), `Veterinarian` (adds a `Consultations` collection). This maps directly to the client/administrator/veterinarian roles in the requirements — role-specific behavior belongs on these subclasses or in services that branch on role, not on `User` itself.
  - A fourth concrete role, `SysAdmin` (`Domain/Entities/SysAdmin.cs`, no extra fields beyond `User`), was added later and is registered as an additional TPH discriminator value (`HasValue<SysAdmin>("SysAdmin")`, see below) and granted the broadest controller access (`[Authorize(Roles = "SysAdmin,Admin")]`/`"SysAdmin,Admin,Veterinarian"`, etc. — always listed first). It is **not** in `Domain/Entities/UserType.cs`'s enum, so `CreateUserDTO.UserType`'s `switch` in `UserServices.AddUserAsync` has no case for it — there is currently no API path that creates a `SysAdmin`; one must be inserted directly in the database (e.g. via the dev seed script or a manual insert) if needed. Treat this as the current state, not a bug to silently fix.
  - `Domain/Entities/UserType.cs` is a plain enum (`Admin`, `Client`, `Veterinarian`) used only at the DTO layer to pick which concrete subclass to instantiate — it is **not** the EF discriminator column (that's the separate `"UserType"` string discriminator from `HasDiscriminator<string>`, below). `CreateUserDTO.UserType` (`[JsonConverter(typeof(JsonStringEnumConverter))]`, defaults to `UserType.Client`) drives a `switch` in `UserServices.AddUserAsync` that constructs a `Client`/`Admin`/`Veterinarian` accordingly. `Dni` is carried on both `CreateUserDTO` and `UserDTO` (`[StringLength(20)]`, nullable) but only ever populated for `Client`s — `AddUserAsync` sets it from `dto.Dni` in the `Client` branch and leaves it out of the `Admin`/`Veterinarian` branches; every `UserDTO` mapping (`GetAllUserAsync`, `GetUserByIdAsync`, and the `Add`/`Update` results) mirrors this with `user is Client client ? client.Dni : null`, and `UpdateUserAsync` overwrites `Dni` only when the target is a `Client` and `dto.Dni` is non-null. `UserDTO.RoleName` (`user.GetType().Name`) is how a caller tells which concrete role a `GET` result is.
- `Pet` belongs to a `Client` (`ClientId` FK) and has many `Consultation`s. All entity IDs and FK properties (`Pet.Id`/`ClientId`, `Consultation.Id`/`PetId`/`VeterinarianId`) are typed as `int`, matching `User.Id` — keep this convention when adding related entities.
- `Domain/Interfaces/IBaseRepository<T>` and its EF-Core-backed `Infrastructure/Repositories/BaseRepository<T>` key all lookups by `int id`, consistent with the `int` entity ID convention.
  - `BaseRepository<T>.GetByIdAsync` returns `null` (via `FirstOrDefaultAsync`) when the id doesn't exist — it does **not** throw; repository-level "not found" is still a plain `null`, only the `Application` layer above it turns that into `NotFoundException` (see Cross-cutting decisions). `UpdateAsync` looks the entity up first and returns `null` if missing, otherwise applies `CurrentValues.SetValues` and saves.
  - `T` must implement `Domain.Interfaces.IEntity` (constrained via `where T : class, IEntity`) rather than relying on reflection over an `Id` property.
- `Consultation` links a `Pet` and a `Veterinarian`, with a `Description` and a `Date` that carries **date and time** (`DateTime`, mapped to a `datetime2` column — it was `date` before, which dropped the time of the appointment). It has **no status field**: a `Status` (`StatusConsultation` enum: `Pending`/`Completed`/`Cancelled`) existed earlier and was deliberately removed, together with the `GET api/consultation/status/{status}` endpoint — don't reintroduce it without asking. This is the appointment/consultation entity referenced by the "agendar turnos" and "historial médico" features. `CreateEditConsultationDTO` is the body of both `POST` and `PUT` (the id comes from the route); `ConsultationDTO` is what `GET`/`POST`/`PUT` return, adding `Id` and `IsDeleted`. Both `AddConsultationAsync` and `UpdateConsultationAsync` validate `PetId` (must resolve via `IPetRepository.GetByIdAsync`) and `VeterinarianId` (must resolve via `IUserRepository.GetByIdAsync` to a `Veterinarian`, not just any `User`) before saving, throwing `BadRequestException` otherwise — same cross-entity-validation convention as `PetServices.AddPetAsync`'s `ClientId` check.
  - **Open question**: how hospitalizations/surgeries should be modeled is not yet decided. Options considered: extend `Consultation` with a `Type` field (Consulta/Cirugía/Internación), or add separate `Surgery`/`Hospitalization` entities linked to `Pet`. Resolve this before implementing the veterinarian's "agendar turnos de cirugías e internaciones" feature.
- "Notificar fin de internación" (listed under the client's functionalities in the requirements doc) is actually the **system notifying the client** that their pet's hospitalization has ended — not a client-initiated action. Model it as a notification triggered by a status change (e.g., a vet/admin marking hospitalization complete), not as an endpoint the client calls.
- `ApplicationDbContext` maps the `User` hierarchy (`Client`/`Admin`/`Veterinarian`/`SysAdmin`) via `HasDiscriminator<string>("UserType")`, i.e. **TPH (Table-Per-Hierarchy)** — note this contradicts the TPT decision this file documented earlier; if TPT is still the intended design, `OnModelCreating` needs `UseTptMappingStrategy()` instead of the discriminator, otherwise treat TPH as the now-current decision. `Pet`/`Consultation` FKs cascade-delete from their parent (`Client`→`Pet`, `Pet`→`Consultation`), while `Consultation`→`Veterinarian` is `Restrict`.

## Cross-cutting decisions

- **Auth**: JWT-based authentication (`Microsoft.AspNetCore.Authentication.JwtBearer`), with **BCrypt** (`BCrypt.Net-Next` package in `Application`, not ASP.NET Core Identity) used for password hashing — `BCrypt.Net.BCrypt.HashPassword(...)`/`BCrypt.Net.BCrypt.Verify(...)`, called directly from `UserServices` (no DI'd hasher abstraction). `UserServices.AddUserAsync`/`UpdateUserAsync` hash `Password` before persisting; `UserServices.AuthenticateAsync(LoginDTO)` looks the user up via `IUserRepository.GetByEmailAsync` and verifies with `BCrypt.Net.BCrypt.Verify`, throwing `Application.Exceptions.UnauthorizedException` (→ `401`, see error-handling convention below) on a bad/missing credential or a soft-deleted user, otherwise returning a `UserDTO` — deliberately populated with only `Id`/`RoleName` (the rest of `UserDTO`'s properties are left at their default, since this DTO instance is only ever read internally by the controller for claim-building, never serialized back to a client; don't reuse this particular `AuthenticateAsync` return value anywhere that expects a fully-populated `UserDTO`). `AuthenticationController.Authenticate` turns that into a JWT (a `sub` claim with `UserDTO.Id` and a `ClaimTypes.Role` claim with `UserDTO.RoleName` — deliberately no email claim) signed with `Authentication:SecretForKey` (HMAC-SHA256), with a per-role expiry chosen by a `switch` on `user.RoleName` (`Client` 1 h, `Veterinarian` 8 h, `Admin`/`SysAdmin` 24 h). A suspended user's existing token stops working immediately: `AddJwtBearer`'s `OnTokenValidated` event in `Program.cs` loads the user by the `sub` claim on every authenticated request and fails authentication (→ `401`) if it is missing or `IsDeleted` — at the cost of one DB lookup per request. `Authentication:Issuer`/`Audience` live in `Web/appsettings.json`; `Authentication:SecretForKey` is deliberately **not** committed — it must be at least 32 characters (HMAC-SHA256), and the team uses the **same value locally and in the deployed dev App Service** (a deliberate choice). It lives only in each developer's `dotnet user-secrets` (`Web` project has a `UserSecretsId`) and in the App Service app setting `Authentication__SecretForKey`. Because it's the real deployed key, it must never go into a committed file — that's why there is no `appsettings.Development.json` holding it. GitHub Actions secrets are **not** used for app configuration: the app reads its config at runtime from App Service environment variables, which are set manually in the portal. Existing DB rows created before this hashing change still have plaintext passwords and won't authenticate until re-saved through `AddUserAsync`/`UpdateUserAsync`. **Role-based authorization is now implemented** (added after the rest of this section was first written — JWT issuance/validation came first, enforcement followed later): every controller action carries an `[Authorize(Roles = "...")]` attribute, per-action on every controller (`UserController`: `"SysAdmin,Admin,Veterinarian"` on each of `GET`/`GET {id}`/`POST`/`PUT`/`DELETE`/`POST {id}/reactivate`, with only a role-less `[Authorize]` at the controller level; same per-action style on `PetController`/`ConsultationController`). On top of that role gate, `UserServices` applies a per-target matrix using the caller's id/role, which `UserController` reads from the claims and passes in: each role **manages** (create/edit/suspend/reactivate) every role below it (rank `SysAdmin` > `Admin` > `Veterinarian` > `Client`, via `Rank` in `UserServices`) — `Client` by `Veterinarian`/`Admin`/`SysAdmin`, `Veterinarian` by `Admin`/`SysAdmin`, `Admin` by `SysAdmin`, `SysAdmin` by nobody, and nobody manages their own role — violations throw `ForbiddenException` (→ `403`). **Visibility**: `SysAdmin` sees everyone, `Admin` everyone but `SysAdmin`s, `Veterinarian` only `Client`s, and every caller sees themself; anything outside that is a `404` (so an `Admin` can't tell a `SysAdmin` exists), and `GET api/user` filters the same way. `DELETE api/user/{id}` **suspends** (`IsDeleted = true`, saved via `UpdateAsync`) instead of removing the row — removing would cascade-delete a `Client`'s pets and consultations — and `POST api/user/{id}/reactivate` sets it back to `false`. For a `Client`, both cascade the same flag onto all of their pets and those pets' consultations (`Pet.IsDeleted`/`Consultation.IsDeleted`, migration `AddPetAndConsultationIsDeleted`, which also backfills clients that were already suspended), mirroring what a physical delete would cascade; there is no separate per-pet or per-consultation soft delete, and `Pet`/`Consultation` have no `DELETE` endpoint at all (the physical deletes were removed so a pet's medical history can't be wiped). The user row is saved last, so a cascade that fails partway is completed by retrying. Suspended users, pets and consultations still appear in listings with `isDeleted: true`, so the frontend can style them. They are read-only: `PetServices.AddPetAsync`/`UpdatePetAsync` throw `BadRequestException` when the target client is suspended or the pet being edited is `IsDeleted`, and `ConsultationServices.AddConsultationAsync`/`UpdateConsultationAsync` do the same for an `IsDeleted` pet or consultation (they still accept a suspended veterinarian). Emails are unique (unique index `IX_Users_Email`, plus a `BadRequestException` check in `AddUserAsync`/`UpdateUserAsync`). The pattern is: every `Pet`/`Consultation` CRUD action (no `DELETE`) is `"SysAdmin,Admin,Veterinarian"`; `PetController`'s `GET api/pet/client/{clientId}` is staff-only (`"SysAdmin,Admin,Veterinarian"`); a `Client` instead uses `GET api/pet/me` (`[Authorize(Roles = "Client")]`), which reads the client id from the `sub` claim. `ConsultationController`'s `GET api/consultation/pet/{petId}` is `"SysAdmin,Admin,Veterinarian,Client"`: for a `Client` the controller derives `clientId` from the `sub` claim and `GetConsultationsByPetIdAsync(petId, clientId)` throws `NotFoundException` if the pet isn't theirs. `GET api/consultation/veterinarian/{veterinarianId}` stays at `"SysAdmin,Admin,Veterinarian"`. There is no veterinarian schedule/availability model: `AddConsultationAsync` doesn't check working hours, overlapping appointments, or past dates, and `Client` can't `POST` a consultation. `AuthenticationController.Authenticate` remains the only unauthenticated endpoint, as it must be. `UserController` also exposes `GET api/user/me` (no role restriction — it inherits only the controller-level `[Authorize]`; the roles are deliberately on each other action, not on the controller, because controller- and action-level `[Authorize]` attributes are combined with AND, so a controller-level role list would also lock `/me` to staff roles) so any authenticated user can fetch their own `UserDTO` by reading the `sub` claim (`ClaimTypes.NameIdentifier` once ASP.NET Core's default inbound claim mapping runs) off `User.FindFirstValue` and calling `GetUserByIdAsync` — this exists precisely because the rest of `UserController` is staff-only, so a `Client` would otherwise have no way to read their own profile. It goes through the same visibility rule, which always lets a caller see themself. The route doesn't collide with `GET api/user/{id:int}` since `{id:int}`'s route constraint never matches the literal `me`. The `[Authorize(Roles = ...)]` checks are enforced purely on the `ClaimTypes.Role` claim set at login time (see above) — resource-level checks exist only where noted above (`GET api/pet/me`, `GET api/consultation/pet/{petId}`, and the user matrix in `UserServices`). List endpoints return `200` with `[]` when empty, never `404`.
- **DTO mapping**: manual mapping (constructors/explicit mapper methods) between `Domain` entities and Application/Web DTOs — no AutoMapper or similar. See `UserServices` for the established pattern.
- **Input validation**: DataAnnotations on the DTOs (mirroring the constraints on the corresponding `Domain` entity) plus `[ApiController]`'s automatic `ModelState` validation — invalid input short-circuits with `400` before the controller action runs.
- **Error handling / "not found"**: services throw `Application.Exceptions.NotFoundException`, `BadRequestException`, `UnauthorizedException` (added for `UserServices.AuthenticateAsync` → `401`), or `ForbiddenException` (the user permission matrix → `403`) instead of returning `null`/`false` or using a tuple return — this **replaces** the earlier null-return/tuple convention (an older iteration of this codebase used bare `null`/`false` plus manual `if (x == null) return NotFound();` checks in every controller action, and `PetServices.UpdatePetAsync` briefly returned a `(PetDTO?, bool)` tuple to distinguish "not found" from "invalid ClientId" before exceptions existed; both are gone now). `Web/ExceptionHandling/AppExceptionHandler.cs` (a .NET 8 `IExceptionHandler`) is the single place that maps exception type → HTTP status code; controllers should never `try/catch` or null-check service results themselves — just call the service and return `Ok`/`CreatedAtAction`/`NoContent` directly, same as `UserController`/`PetController`. Cross-entity validation (e.g. `Pet.ClientId` must reference an existing `Client`) now throws `BadRequestException` from `PetServices.AddPetAsync`/`UpdatePetAsync` (both inject `IUserRepository` and check `is not Client`) instead of returning `null`/a tuple. Any exception type not handled by `AppExceptionHandler` falls through to the default 500 behavior, so add a case there (not a controller-level catch) when a new failure mode needs its own status code.
- **Persistence**: SQL Server via EF Core/`Microsoft.EntityFrameworkCore.SqlServer`, hosted on **Azure SQL Database** (decided — see Architecture/Infrastructure above). This replaces the earlier Postgres/Supabase setup; a local-SQLite alternative was evaluated and explicitly rejected in favor of this. Two separate Azure SQL databases, one per environment, each in its own Azure resource group (dev and prod resource groups already exist; a teammate provisions the actual SQL servers/databases — not something driven from this repo). `Web/appsettings.json`'s `ConnectionStrings:DefaultConnection` is deliberately left empty — the real value is supplied per-environment, never committed: locally via `dotnet user-secrets set "ConnectionStrings:DefaultConnection" "..."` (mirrors the existing `Authentication:SecretForKey` pattern, same `UserSecretsId`), and in the deployed Azure App Service via an app setting named `ConnectionStrings__DefaultConnection` (set manually in the Azure portal/CLI). The GitHub Actions workflow at `.github/workflows/main_pet-sys-app.yml` (one level up from this solution) follows the class reference repo (`github.com/PabloPaezSheridan/pl2026_classapi`): push to `main` deploys the `dev` GitHub Environment; `workflow_dispatch` lets you pick `dev`/`prod`. The deploy job logs into Azure, restores the `dotnet-ef` local tool, adds the runner's public IP to the SQL server firewall (`github-runner-${{ github.run_id }}`), wakes the auto-paused database (`SELECT 1`, 3 attempts), runs `dotnet ef database update` with `ConnectionStrings__DefaultConnection` from the secret, removes the firewall rule (`if: always()`), then deploys to the App Service named by `vars.AZURE_WEBAPP_NAME` (a deviation from the reference, which hardcodes the dev app name). Per-environment GitHub config it expects — **secrets**: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_SQL_CONNECTION_STRING`; **variables**: `AZURE_SQL_RESOURCE_GROUP`, `AZURE_SQL_SERVER_NAME`, `AZURE_WEBAPP_NAME`. The `azure/login` identity needs rights on the SQL server (firewall rules) as well as the App Service. The App Service itself still needs its runtime app settings (`ConnectionStrings__DefaultConnection`, `Authentication__SecretForKey`) set in the portal — the workflow doesn't push them. `main` is the **dev** branch (App Service `pet-sys-app`); prod has its own Azure SQL server/database/App Service and is deployed via the `prod` environment. Azure SQL access: the server firewall has "Allow Azure services" enabled (so the App Service connects), and each developer's public IP must be added to the server's firewall (Networking) to connect from their machine — home/university IPs change, so re-add when a connection is refused.
  - **Dev seed data**: `Scripts/seed-dev.sql` is a plain T-SQL script (not a project, not part of the build) that fills the **dev** Azure SQL database with test data — 105 users (5 `Admin`, 15 `Veterinarian`, 85 `Client`), 20 pets, 40 consultations — run manually from SSMS/Azure Data Studio/the Azure portal query editor/`sqlcmd` after the schema exists (i.e. after the first deploy has run the migrations). It inserts explicit IDs (`SET IDENTITY_INSERT`), writes the TPH discriminator `UserType` directly, does nothing if `Users` already has rows, and dates consultations relative to `GETDATE()` (each with a time between 09:00 and 18:00). Every seeded user's password is `Password123!` (a single precomputed BCrypt hash). Because it's raw SQL against the table schema, it must be updated by hand whenever a migration changes `Users`/`Pets`/`Consultations`. The prod database intentionally starts empty (schema only, via the workflow's migration step).
  - **Known issue (historical)**: the old Supabase connection string (with password) was committed in plaintext in `Web/appsettings.json` before this migration. The string has been removed from the file, but it's still present in git history — the Supabase credential should still be rotated independently of this change.
- **Testing**: no test project exists yet on `main`; framework not decided.
- **Date inputs**: DTO dates are `DateTime?`/`DateOnly?` so `[Required]` actually rejects a missing value (a non-nullable `DateTime` defaults to `0001-01-01` and passes); services map with `.Value`. Entities keep non-nullable types.
- **Frontend**: a separate SPA (React/Angular/etc., own repo) will consume this API. `Web/Program.cs` registers a permissive CORS policy (`"AllowAll"`: `AllowAnyOrigin`/`AllowAnyMethod`/`AllowAnyHeader`) applied globally via `app.UseCors("AllowAll")` before `UseAuthorization()` — fine for now with no auth, but tighten this (specific origins, not any) once JWT auth lands so credentials/tokens aren't exposed to arbitrary origins.
